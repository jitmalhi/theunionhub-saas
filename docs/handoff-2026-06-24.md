## 3 · Member Hub — vision & design

**File:** [docs/representation-design.md](./representation-design.md)

The strategic reframe: the card is the member's **front door** into a hub
(Representation · Help · Knowledge · Engagement · Verification). The moat is the
accumulated relational/temporal data, not the QR code.

**Design decisions locked by the product owner:**

| # | Decision |
|---|----------|
| 1 | `/access/:uuid` keys off the **member id** |
| 2 | Position taxonomy: `steward / backup_steward / unit_officer / staff_rep` |
| 3 | The page shows the **full team**, not a single contact |
| 4 | Rep data → admin roster tool eventually; **seeded** for Phase 0 |
| 5 | Engagement tracking is **aggregate-only** (member privacy) |

**Key architectural principle:** assign members to **positions (seats)**, not to
people. A separate time-bounded table records who holds each seat — so a steward
retiring is a hand-off that never breaks a member's link. This is what makes the
"continuity" feature work.

### Security model (mirrors existing patterns)
- `get_representation_team` is `SECURITY DEFINER` and re-derives the tenant from
  `x-tenant-id` itself (via `get_request_tenant_id()`) — a member id from another
  tenant returns nothing. Same shape as `lookup_member` (migration 0008).
- Anon **never** selects the spine tables directly; it reads only through the
  RPC. `authenticated` admins get a tenant-scoped read for the future roster
  tool. No INSERT/UPDATE/DELETE policies yet (writes will come via admin RPCs).
- The page validates the UUID, escapes DB output, and `encodeURIComponent`s
  `mailto:`/`tel:` links.

## 5 · Local environment — why `supabase db reset` won't run

Diagnosed on the Windows box (this **is** the local machine — the agent's
terminal runs here, not elsewhere). Three independent blockers:

1. **Broken CLI:** the `supabase` on PATH (`C:\nvm4w\nodejs\supabase.ps1`) is an
   npm shim whose platform binary (`@supabase/cli-windows-x64\bin\supabase.exe`)
   was never downloaded → `ENOENT`. (npm is a deprecated install path for the
   Supabase CLI.)
2. **No Docker** — `supabase start` / `db reset` run the local stack as Docker
   containers. None installed.
3. **No `supabase/config.toml`** — the repo was never `supabase init`'d as a
   local CLI project.

→ Pivoted to the **hosted SQL-editor apply path** (no Docker/CLI needed). The
repo's existing `_consolidated*.sql` files suggest this is already the project's
manual-apply pattern.
